01
Performance · JPA

채팅방 목록 조회의 N+1 문제

"목록 하나를 그리는 데 쿼리가 몇 번 나가는가"
문제 원인

매칭이 성사되면 채팅방이 생성되고, 사용자는 자신의 채팅방 목록을 조회합니다. 채팅방에는 뽑은 사람(picker)과 뽑힌 사람(picked)이 연관되어 있고, 각 사용자에는 프로필 특징 정보(UserAiFeature)가 다시 연관되어 있습니다. 연관관계를 지연 로딩으로 두고 목록을 조회하면, 목록 쿼리 1번 이후 방마다 상대 정보를 꺼낼 때 추가 쿼리가 발생합니다. 방이 N개면 최대 1 + 4N번 — 사용자가 늘수록 조회 비용이 목록 크기에 비례해서 커지는 구조였습니다.

해결 과정

연관 엔티티를 Fetch Join으로 한 번에 로딩

// ChatRoomRepository — 목록 조회 시 필요한 연관을 전부 명시
@Query("SELECT cr FROM ChatRoom cr " +
    "JOIN FETCH cr.picker p " +
    "JOIN FETCH p.userAiFeature " +
    "JOIN FETCH cr.picked pk " +
    "JOIN FETCH pk.userAiFeature " +
    "WHERE cr.picker = :user OR cr.picked = :user")
List<ChatRoom> findAllWithUsersByUser(@Param("user") Users user);
의사결정 근거
해결 방법은 여러 가지가 있었습니다. 배치 사이즈(default_batch_fetch_size)는 쿼리를 줄여주지만 없애지는 못하고, EntityGraph는 선언은 간단하지만 조건이 붙는 순간 관리가 어려워집니다. 채팅방 목록은 "화면에 무엇이 필요한지가 명확하게 고정된 조회"였기 때문에, 필요한 연관을 쿼리에 명시하는 Fetch Join이 의도를 가장 정확하게 드러낸다고 판단했습니다.
놓치기 쉬운 포인트
Fetch Join은 만능이 아닙니다. 컬렉션을 2개 이상 Fetch Join하면 예외가 발생하고(MultipleBagFetchException), 페이징과 함께 쓰면 메모리에서 페이징이 일어납니다. 이 조회는 ToOne 연관만 걸려 있어 안전했습니다 — "어떤 연관인지 확인하고 쓰는 것"까지가 이 도구의 사용법이라고 생각합니다.
결과
  • 채팅방 N개 조회 시 최대 1 + 4N번 나가던 쿼리를 1번으로 줄였습니다
  • 목록 크기와 무관하게 조회 비용이 일정해졌습니다
  • 같은 기준으로 취미 목록(UserAiFeature ↔ hobbyList) 조회에도 Fetch Join을 적용했습니다
02
Payment · Idempotency

PG 도입을 대비한 결제 멱등성 설계

"승인 요청은 몇 번을 보내도 결과가 한 번이어야 한다"
배경

실제 운영에서 결제는 계좌이체로 진행했지만, PG(토스페이먼츠) 도입을 준비하며 결제 승인·취소 흐름을 미리 구현해 두었습니다. 결과적으로 업종 제한 때문에 PG를 붙이지 못했지만, 이 과정에서 "결제 요청이 중복으로 들어오면 어떻게 되는가"를 설계의 중심에 두게 됐습니다. 사용자의 연타, 네트워크 타임아웃 후 재시도 — 같은 승인 요청이 두 번 들어오는 경로는 생각보다 많습니다.

해결 과정

① 승인 전 3가지 검증 — 상태 · 금액 · 멱등키

private void validateOrder(Orders order, String idempotencyKey, Long amount) {
    // 1. 주문 상태 검증 — 이미 처리된 주문의 재승인 차단
    if (!order.getOrderStatus().equals(OrderStatus.ORDER_REQUEST)) {
        throw new BusinessException(ResponseCode.BAD_REQUEST);
    }
    // 2. 금액 검증 — 클라이언트 금액 위변조 차단
    if (!order.getAmount().equals(amount)) {
        throw new BusinessException(ResponseCode.BAD_REQUEST);
    }
    // 3. 멱등키 검증 — 같은 요청의 중복 실행 차단
    if (!payRedisService.isIdempotent(idempotencyKey, order.getOrderUuid())) {
        throw new BusinessException(ResponseCode.BAD_REQUEST);
    }
}

② 멱등키는 Redis SETNX로 원자적으로 선점

public boolean isIdempotent(String idempotencyKey, String orderUUID) {
    String redisKey = "idempotency-key:" + idempotencyKey;

    // 키가 없을 때만 저장 성공 — "검사 후 저장"이 아니라 한 번의 원자적 연산
    Boolean isSet = redisTemplate.opsForValue()
        .setIfAbsent(redisKey, orderUUID, Duration.ofMinutes(5));

    return isSet != null && isSet;
}
의사결정 근거
"Redis에서 키를 조회하고, 없으면 저장한다"를 두 번의 연산으로 하면 그 사이에 다른 요청이 끼어들 수 있습니다. SETNX(setIfAbsent)는 확인과 저장을 하나의 원자적 연산으로 처리하므로, 동시에 들어온 두 요청 중 정확히 하나만 통과합니다. TTL 5분은 "같은 결제 의도의 재시도가 유효한 시간"으로 정했습니다.

③ 승인 후 실패 시 자동 취소

try {
    // 승인 성공 후 주문 상태 변경 · 포인트 지급 등 후처리
    ...
} catch (Exception e) {
    // 후처리 실패 시 자동 취소 요청 — "PG에는 승인됐는데 우리 DB엔 없는 상태"를 방치하지 않음
    requestTossPaymentCancel(paymentKey, tempIdempotencyKey, order, cancelReason);
    order.updateOrderStatus(OrderStatus.ORDER_REFUND);
    return false;
}
놓치기 쉬운 포인트
"우리 서버에서 예외가 났다"가 "PG에서도 실패했다"는 뜻이 아닙니다. 승인은 성공했는데 우리 쪽 후처리만 실패하는 경우, 자동 취소까지 설계해 두지 않으면 돈은 빠져나갔는데 상품은 지급되지 않은 상태가 남습니다. 실패 경로의 복구를 정상 경로와 함께 설계했습니다.
결과
  • 중복 승인·취소 요청이 PG API 호출 전에 차단되는 구조를 만들었습니다
  • 상태·금액·멱등키 3단계 검증으로 재승인과 금액 위변조를 함께 방어합니다
  • 후처리 실패 시 자동 취소로 정합성이 깨진 상태가 남지 않게 했습니다
03
Auth · Security

JWT에서 세션으로 — 인증 방식을 바꾼 이유

"토큰을 누가 들고 있느냐가 통제 범위를 결정한다"
문제 원인

처음에는 JWT 기반 인증으로 시작했습니다. 액세스 토큰과 리프레시 토큰을 발급하고, 리프레시 토큰은 쿠키에 담아 Redis 저장본과 대조하는 구조였습니다. 그런데 운영을 준비하며 이 구조의 약점이 눈에 들어왔습니다. JWT는 발급되는 순간 서버의 손을 떠납니다. 토큰이 탈취되어도 만료 시각까지는 유효하고, 서버가 "이 토큰은 이제 무효"라고 선언할 방법이 기본적으로는 없습니다.

해결 과정

세션 + Redis로 전환 — 무효화 권한을 서버로

// SecurityConfig — 세션 기반 인증으로 전환
http
    .sessionManagement(session -> session
        .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
        .invalidSessionUrl("https://comatching.site")
    );

http
    .logout(logout -> logout
        .logoutUrl("/logout")
        .deleteCookies("JSESSIONID")     // 클라이언트에는 세션 식별자만 남음
        .invalidateHttpSession(true)      // 서버에서 세션을 즉시 파기
    );

세션 저장소는 spring-session-data-redis로 Redis에 두었습니다. 서버가 여러 대가 되어도 세션을 공유할 수 있고, 이상 징후가 보이면 서버에서 해당 세션을 즉시 파기할 수 있습니다. 기존 JWT 리프레시 토큰 코드는 @Deprecated로 남겨 전환의 흔적을 기록했습니다.

의사결정 근거
표준적으로 인증 상태는 "누가 들고 있느냐"의 트레이드오프입니다. JWT(클라이언트 보관)는 서버가 상태를 갖지 않아 확장에 유리하지만, 발급 후 통제가 어렵습니다. 세션(서버 보관)은 서버가 상태 관리 비용을 지불하는 대신, 무효화 권한을 서버가 가집니다. 당시 코매칭은 단일 서버 규모였고 stateless 확장의 이점을 누릴 일이 없었기 때문에, 탈취 대응이 가능한 세션 쪽이 얻는 것이 더 많다고 판단했습니다.
이 선택의 다음 이야기
MSA로 재설계한 코매칭 v5에서는 다시 JWT로 돌아갑니다. 게이트웨이가 상태 없이 토큰을 검증해야 했기 때문입니다. 다만 이때는 세션에서 배운 "서버가 무효화 권한을 가져야 한다"를 Refresh Token Rotation과 로그아웃 토큰 Denylist로 구현했습니다. 자세한 내용은 코매칭 v5에서 다룹니다.
결과
  • 탈취 의심 시 서버에서 세션을 즉시 무효화할 수 있는 구조가 됐습니다
  • 클라이언트 쿠키에는 토큰 대신 세션 식별자만 남습니다
  • Redis 세션 저장소로 서버 증설 시에도 세션 공유가 가능하게 준비했습니다
Key Takeaways
01
조회 비용은 데이터가 아니라 구조가 결정합니다 — N+1은 데이터가 늘어난 뒤에야 보입니다. 목록 조회를 만들 때 쿼리가 몇 번 나가는지 먼저 세는 습관이 생겼습니다.
02
실패 경로도 정상 경로와 함께 설계해야 합니다 — 멱등성 검증과 자동 취소는 "잘 되는 경우"가 아니라 "잘못되는 경우"를 위한 코드입니다. 결제처럼 되돌리기 어려운 도메인일수록 실패 설계가 먼저입니다.
03
인증 방식에 정답은 없습니다 — JWT와 세션은 우열이 아니라 "통제와 확장성 중 지금 무엇이 필요한가"의 문제였습니다. 서비스 규모가 바뀌면 답도 바뀐다는 것을 v5에서 다시 확인했습니다.
