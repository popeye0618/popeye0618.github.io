01
Concurrency · Distributed Lock

분산 락과 비관적 락의 이중 방어

"서버가 여러 대가 되는 순간, synchronized는 아무것도 지켜주지 못한다"
문제 원인

v3 운영에서 정합성이 깨지는 사건을 겪었습니다. "한 사용자는 최대 5회까지 뽑힐 수 있다"는 정책이 있었는데, 뽑힌 횟수를 락 없이 DB 컬럼으로 세다 보니 동시 요청이 겹치면 5회를 초과하는 사용자가 실제로 나왔습니다. v5는 여기에 조건이 하나 더 붙습니다 — 서비스가 여러 인스턴스로 뜨는 분산 환경이라, 한 JVM 안에서만 유효한 동기화로는 아무것도 보장할 수 없습니다.

해결 과정

① 어노테이션 하나로 선언하는 Redisson 분산 락 AOP

// common-module — 모든 서비스가 공유하는 분산 락 AOP
@Around("@annotation(com.comatching.common.annotation.DistributedLock)")
public Object lock(ProceedingJoinPoint joinPoint) throws Throwable {

    // SpEL로 파라미터 기반 락 키 생성 — 예: "MATCHING_REQUEST:42"
    String key = distributedLock.key() + ":" + CustomSpringELParser.getDynamicValue(
        signature.getParameterNames(), joinPoint.getArgs(), distributedLock.identifier());

    RLock rLock = redissonClient.getLock(key);

    boolean available = rLock.tryLock(
        distributedLock.waitTime(), distributedLock.leaseTime(), distributedLock.timeUnit());

    if (!available) {
        throw new BusinessException(GeneralErrorCode.TOO_MANY_REQUEST);
    }

    // 락 안에서 새 트랜잭션 실행 — 락 해제 전에 커밋이 완료되도록 보장
    return aopForTransaction.proceed(joinPoint);
}
// matching-service — 매칭 요청은 유저 단위로 직렬화 ("따닥" 차단)
@DistributedLock(key = "MATCHING_REQUEST", identifier = "#memberId", leaseTime = 15L)
public MatchingResponse requestMatching(Long memberId, MatchingRequest request) { ... }

// item-service — 매칭권 차감도 유저+아이템 단위로 직렬화
@DistributedLock(key = "item:inventory", identifier = "#memberId + ':' + #itemType", leaseTime = 10L)
public void useItem(Long memberId, ItemType itemType, int count) { ... }
놓치기 쉬운 포인트 — 락과 트랜잭션의 순서
락 획득 → 트랜잭션 시작 → 커밋 → 락 해제 순서가 지켜져야 합니다. 만약 트랜잭션이 락 바깥에서 시작되면, 락은 풀렸는데 커밋은 아직인 순간에 다음 요청이 진입해서 커밋 전의 값을 읽을 수 있습니다. 그래서 AOP가 락 안에서 새 트랜잭션(REQUIRES_NEW)을 열도록 분리했습니다.

② DB 레벨의 마지막 방어선 — 비관적 락

// item-service ItemRepository — 재고 행은 DB에서도 잠근다
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT i FROM Item i WHERE i.memberId = :memberId AND i.itemType = :itemType")
Optional<Item> findByMemberIdAndItemTypeForUpdate(...);
의사결정 근거 — 왜 이중으로 잠그는가
분산 락만으로 충분해 보이지만, 락의 leaseTime이 만료되는 순간이 있습니다. 로직이 예상보다 오래 걸려 락이 먼저 풀리면 두 요청이 동시에 재고를 만질 수 있습니다. 분산 락은 "동시 진입을 거의 다 막는 1차 방어", 비관적 락은 "그래도 뚫린 요청을 DB가 직렬화하는 최후 방어"로 역할을 나눴습니다. v3에서 정합성이 깨지는 걸 겪어봤기 때문에, 정합성이 돈과 연결된 곳(재고·매칭권)은 겹쳐서 방어하기로 했습니다.
결과
  • 매칭 요청 · 재고 차감 · 주문 생성 등 6개 경로에 유저 단위 분산 락을 선언형으로 적용했습니다
  • v3에서 겪은 "5회 초과 뽑힘" 유형의 정합성 문제가 구조적으로 재발할 수 없게 됐습니다
  • 락 획득 실패는 429(TOO_MANY_REQUEST)로 응답해 사용자 연타를 자연스럽게 흡수합니다
02
Communication · Kafka vs OpenFeign

동기와 비동기 — 통신 방식의 선택 기준

"지금 이 응답이 없으면 다음 줄을 실행할 수 없는가"
문제 원인

모놀리스에서는 메서드 호출이면 끝나던 일이, MSA에서는 전부 네트워크 통신이 됩니다. 채팅방 목록에 상대 프로필을 보여주려면 user-service에 물어봐야 하고, 매칭이 성사되면 chat-service가 채팅방을 만들어야 하고, 채팅이 오면 notification이 푸시를 보내야 합니다. 이걸 전부 동기 호출로 엮으면 한 서비스의 장애가 호출 체인을 타고 전파되고, 전부 비동기로 하면 당장 필요한 응답을 기다릴 방법이 없습니다. 기준이 필요했습니다.

해결 과정

① 즉시 응답이 필요한 조회 — OpenFeign (동기)

// chat-service — 채팅방 목록을 그리려면 지금 프로필이 필요하다
@FeignClient(name = "user-service", path = "/api/internal/users", url = "${user-service.url}")
public interface MemberClient {

    // 방마다 1번씩 N번 호출하지 않도록 벌크 API로 설계
    @PostMapping("/profiles/bulk")
    List<ProfileResponse> getProfiles(@RequestBody List<Long> memberIds);
}

② 결과만 전달하면 되는 흐름 — Kafka (비동기)

// matching-service — 매칭 성사를 알리고 즉시 응답을 반환
kafkaTemplate.send("matching-success-topic", event);

// chat-service — 이벤트를 구독해 채팅방을 생성
@KafkaListener(topics = "matching-success-topic", groupId = "chat-service")
public void consumeMatchingSuccess(MatchingSuccessEvent event) {
    chatRoomService.createRoom(event);
}

// notification — 채팅 이벤트를 구독해 FCM 푸시 발송
@KafkaListener(topics = "chat-notification", groupId = "notification")
public void consume(ChatMessageEvent event) {
    fcmService.sendNotification(event);
}
의사결정 근거
기준은 하나였습니다. "이 응답이 없으면 다음 줄을 실행할 수 없는가?" 프로필 조회는 없으면 화면을 못 그리니 동기(Feign)입니다. 대신 벌크 API로 호출 횟수를 줄였습니다. 푸시 알림·채팅방 생성·회원가입 데이터 동기화는 "언젠가 처리되면 되는 일"이니 비동기(Kafka)입니다. 덤으로 notification이 죽어 있어도 채팅 저장은 성공하고, 밀린 알림은 복구 후 소비됩니다 — 장애 격리가 통신 방식 선택에 따라오는 걸 확인했습니다.
결과
  • 조회 3종(프로필·매칭이력·재고)은 Feign + 벌크 API, 알림·동기화 3종은 Kafka 이벤트로 분리했습니다
  • notification 장애가 채팅 기능에 전파되지 않는 구조를 확인했습니다
  • "MSA에서는 조인이 안 된다"는 문제를 벌크 내부 API라는 형태로 풀었습니다

Auth · Token Security

Refresh Token Rotation과 게이트웨이 Denylist

"세션에서 배운 것을 JWT 위에 다시 구현하기"
문제 원인

v3에서는 토큰 탈취에 대응하기 위해 JWT를 버리고 세션으로 갔습니다. 그런데 MSA에서는 사정이 다릅니다. 게이트웨이가 모든 요청을 상태 없이 검증해야 하므로 JWT가 사실상 강제됩니다. 그렇다면 질문이 돌아옵니다 — 세션으로 얻었던 "서버의 무효화 권한"을, JWT 위에서는 어떻게 되찾을 것인가.

해결 과정

① Refresh Token Rotation — 재사용을 탈취 신호로 간주

// user-service AuthServiceImpl — 재발급 요청 처리
public TokenResponse reissue(String refreshToken) {

    Claims claims = jwtUtil.parseToken(refreshToken);
    long memberId = Long.parseLong(claims.getSubject());

    RefreshToken redisToken = refreshTokenRepository.findById(memberId)
        .orElseThrow(() -> new BusinessException(UNAUTHORIZED));

    // Redis 저장본과 불일치 = 이미 사용된(회전된) 토큰의 재사용 → 탈취 가능성
    if (!redisToken.getToken().equals(refreshToken)) {
        refreshTokenRepository.delete(redisToken);   // 세션 전체 무효화 → 강제 재로그인
        throw new BusinessException(UNAUTHORIZED);
    }

    // 액세스·리프레시 모두 새로 발급하고 Redis 갱신 — 리프레시 토큰은 1회용
    String newAccessToken  = jwtUtil.createAccessToken(...);
    String newRefreshToken = jwtUtil.createRefreshToken(memberId);
    refreshTokenRepository.save(new RefreshToken(memberId, newRefreshToken));

    return new TokenResponse(newAccessToken, newRefreshToken);
}

② 게이트웨이 — Denylist 검사와 인증 헤더 주입

// gateway-service AuthorizationHeaderFilter
if (!jwtUtil.validateToken(accessToken)) { return unauthorized(exchange); }

Claims claims = jwtUtil.parseToken(accessToken);

// 로그아웃된 토큰인지 검사 — jti 기반 Denylist (Redis)
return accessTokenDenylistService.isDenied(claims.getId())
    .flatMap(denied -> {
        if (denied) { return unauthorized(exchange); }

        return chain.filter(exchange.mutate()
            .request(builder -> builder.headers(headers -> {
                // 클라이언트가 위조해서 보낸 헤더를 먼저 제거 — 스푸핑 방지
                headers.remove("X-Member-Id");
                headers.remove("X-Member-Email");
                headers.remove("X-Member-Role");
                // 검증된 값으로 다시 주입 — 내부 서비스는 이 헤더만 신뢰
                headers.add("X-Member-Id", memberId);
                ...
            })).build());
    });
의사결정 근거
JWT의 약점은 "발급 후 통제 불가"입니다. 이걸 두 겹으로 보완했습니다. RTR은 리프레시 토큰을 1회용으로 만들어, 탈취범과 원래 사용자 중 누구든 먼저 쓰는 순간 다른 쪽의 재사용이 감지되고 세션 전체가 무효화됩니다. Denylist는 로그아웃한 액세스 토큰의 남은 유효시간을 차단합니다. 결국 v3의 세션이 주던 "서버가 끊을 수 있는 권한"을, stateless 검증을 유지하면서 되찾은 셈입니다.
놓치기 쉬운 포인트 — 헤더 스푸핑
내부 서비스는 게이트웨이가 넣어준 X-Member-Id를 신뢰합니다. 그런데 클라이언트가 이 헤더를 직접 넣어 보내면? 게이트웨이가 주입 전에 같은 이름의 헤더를 제거하지 않으면 인증 우회가 됩니다. 신뢰 경계를 만들 때는 "신뢰할 값을 넣는 것"만큼 "신뢰할 수 없는 값을 지우는 것"이 중요했습니다.
결과
  • 리프레시 토큰 재사용이 감지되면 세션 전체가 즉시 무효화됩니다
  • 로그아웃 후 남은 액세스 토큰은 게이트웨이에서 차단됩니다
  • 내부 서비스는 인증 로직 없이 검증된 헤더만 신뢰하면 되는 구조가 됐습니다
04
Cache · Data Store

채팅 차단 목록 캐싱과 저장소 선택

"메시지 한 건마다 실행되는 조회는 비용이 다르다"
문제 원인

채팅에는 차단 기능이 있습니다. 문제는 검사 위치입니다 — 메시지가 한 건 올 때마다 "수신자가 발신자를 차단했는가"를 확인해야 합니다. 채팅방 목록을 그릴 때도 차단한 상대를 걸러야 합니다. 차단 데이터 자체는 거의 바뀌지 않는데, 조회는 채팅 트래픽에 비례해서 일어나는 전형적인 읽기 편중 패턴이었습니다.

해결 과정

Cache-Aside + 쓰기 시점 무효화

// chat-service BlockServiceImpl
private static final String BLOCK_CACHE_KEY_PREFIX = "user:block:";
private static final Duration CACHE_TTL = Duration.ofMinutes(30);

public Set<Long> getBlockedUserIds(Long blockerUserId) {
    String cacheKey = BLOCK_CACHE_KEY_PREFIX + blockerUserId;

    Object cached = redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) { return toSet(cached); }      // 캐시 히트

    Set<Long> blockedIds = loadFromDb(blockerUserId);     // 미스 → DB 조회
    redisTemplate.opsForValue().set(cacheKey, blockedIds, CACHE_TTL);
    return blockedIds;
}

public void blockUser(Long blockerUserId, Long blockedUserId) {
    userBlockRepository.save(...);
    evictBlockCache(blockerUserId);   // 쓰기 시점에 캐시 무효화 — 다음 조회가 새로 적재
}
의사결정 근거 — TTL과 무효화를 둘 다 쓰는 이유
차단은 즉시 반영되어야 하는 기능입니다. TTL만 쓰면 최대 30분간 차단이 안 먹힐 수 있으니, 차단/해제 시점에 캐시를 지워 다음 조회가 DB에서 새로 읽게 했습니다. 그럼 TTL은 왜 남겼는가 — 무효화 로직에 버그가 있거나 Redis에 잔여 키가 남는 경우를 위한 안전장치입니다. "일관성은 무효화가 책임지고, TTL은 실패의 상한선을 정한다"로 역할을 나눴습니다.
함께 내린 선택 — 채팅 메시지는 왜 MongoDB인가
채팅 메시지는 수정 없이 쌓이기만 하고, 조회는 방 단위 시간순뿐이라 RDB의 트랜잭션·조인·정합성 제약을 쓸 일이 없는 데이터입니다. 서비스에서 가장 빠르게 늘어나는 데이터이기도 해서, 스키마 변경과 수평 확장이 쉬운 MongoDB에 (roomId, createdAt) 복합 인덱스 하나로 저장했습니다. 반대로 정합성이 중요한 회원·주문·재고는 MySQL에 그대로 뒀습니다 — 서비스별로 데이터 특성에 맞는 저장소를 고를 수 있다는 것이 MSA에서 체감한 이점이었습니다.
결과
  • 메시지 수신·채팅방 목록·실시간 중계(Pub/Sub) 3개 경로의 차단 검사가 캐시를 공유합니다
  • 차단/해제는 즉시 반영되면서, 반복 조회는 DB에 도달하지 않습니다
  • 데이터 특성에 따라 MySQL과 MongoDB를 분리 운용하는 경험을 얻었습니다
Key Takeaways
01
분산 환경의 동시성은 겹쳐서 방어해야 합니다 — 분산 락에도 leaseTime 만료라는 구멍이 있습니다. 돈과 연결된 정합성은 분산 락 + DB 락으로 층을 나눠 지키는 것이 맞다고 판단했습니다.
02
통신 방식은 취향이 아니라 기준의 문제입니다 — "이 응답이 없으면 다음 줄을 실행할 수 없는가"라는 질문 하나로 동기/비동기가 갈렸고, 장애 격리는 그 선택을 따라왔습니다.
03
