01
Storage · Security

S3 Presigned URL과 Strategy 패턴

"버킷은 잠그고, 업로드는 서버를 거치지 않게"
문제 원인

네컷사진 서비스의 본질은 파일입니다. 사진 원본, 합성 결과물, 프레임 에셋, 프로필 이미지 — 전부 크기가 크고 자주 오갑니다. 파일을 서버로 받아 S3에 올리는 방식은 서버 메모리와 대역폭을 파일 크기만큼 소모하고, 업로드가 몰리면 API 서버 전체가 느려집니다. 그렇다고 버킷을 공개로 열면 누구나 URL로 원본에 접근할 수 있습니다. 보안(비공개 버킷)과 성능(서버 우회)을 동시에 잡아야 했습니다.

해결 과정

① 업로드·조회 모두 Presigned URL — 버킷은 완전 비공개

// S3FileStorageService — 업로드용 PUT Presigned URL 발급
public PresignedUploadResponse generatePresignedUploadUrl(UploadType type, String filename) {
    UploadPathStrategy strategy = strategyMap.get(type);
    String key = strategy.generateKey(publicId, filename, true);  // temp 경로로 발급

    PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
        .signatureDuration(Duration.ofMinutes(10))   // 업로드 권한은 10분만
        .putObjectRequest(r -> r.bucket(bucket).key(key))
        .build();

    return new PresignedUploadResponse(key, s3Presigner.presignPutObject(presignRequest).url());
}

// 조회도 서명된 URL로만 — 비공개 버킷 유지
public String generatePresignedGetUrl(String key) {
    GetObjectPresignRequest presignRequest = GetObjectPresignRequest.builder()
        .signatureDuration(EXPIRY)                    // 조회는 1일
        .getObjectRequest(r -> r.bucket(bucket).key(key))
        .build();
    return s3Presigner.presignGetObject(presignRequest).url().toString();
}

② 업로드 경로 규칙은 Strategy 패턴으로 분리

public interface UploadPathStrategy {
    UploadType getUploadType();
    String generateKey(String publicId, String originalFilename, boolean isTemp);
}

// 구현체: FrameUploadPathStrategy · FourcutPhotoUploadPathStrategy
//        ProfileUploadPathStrategy · FrameComponentUploadPathStrategy
// 스프링이 구현체들을 Map으로 주입 — 업로드 유형 추가 시 구현체 하나만 늘어난다
의사결정 근거 — temp 업로드 후 승격
Presigned URL을 발급해도 사용자가 실제로 업로드를 완료할지는 알 수 없습니다. 그래서 업로드는 temp 경로로 먼저 받고, 저장 확정 시점에 copyObject로 정식 경로로 승격합니다. 업로드 도중 이탈한 파일은 temp에만 남아 정리 대상이 명확해지고, 정식 경로에는 확정된 파일만 존재한다는 불변식이 생깁니다.
결과
  • 파일이 서버를 거치지 않아 API 서버의 메모리·대역폭 사용이 파일 크기와 무관해졌습니다
  • 버킷을 완전 비공개로 유지하면서 업로드 10분·조회 1일의 시간 제한 접근만 허용합니다
  • 업로드 유형 4종의 경로 규칙이 Strategy 구현체로 분리되어 유형 추가가 기존 코드를 건드리지 않습니다
02
Reliability · AOP

중복 요청 차단 AOP — FAIL_OPEN과 FAIL_CLOSE

"Redis가 죽었을 때, 기능을 열 것인가 막을 것인가"
문제 원인

메일 인증 발송 버튼을 빠르게 두 번 누르면("따닥") 인증 메일이 두 통 발송됩니다. 이런 중복 요청 차단은 여러 엔드포인트에 필요한 공통 관심사라 AOP로 분리했는데, 구현 중에 더 어려운 질문을 만났습니다 — 차단 장치가 의존하는 Redis 자체가 장애라면? 차단을 못 하니 요청을 전부 거부할 것인가, 아니면 중복을 감수하고 전부 통과시킬 것인가. 정답이 하나가 아니라는 것이 이 문제의 본질이었습니다.

해결 과정

① SpEL 키 + Redis SETNX 기반 차단 AOP

@Around("@annotation(preventDuplicateRequest)")
public Object checkDuplicate(ProceedingJoinPoint joinPoint,
                             PreventDuplicateRequest preventDuplicateRequest) throws Throwable {

    // SpEL로 파라미터에서 키 추출 — 예: "#request.email"
    String uniqueKey = generateUniqueKey(joinPoint, preventDuplicateRequest.key());
    String redisKey = "duplicate:request:" + uniqueKey;

    try {
        Boolean isSuccess = redisTemplate.opsForValue()
            .setIfAbsent(redisKey, "locked", Duration.ofMillis(unit.toMillis(time)));

        if (isSuccess == null || !isSuccess) {
            throw new BusinessException(GlobalErrorCode.DUPLICATE_REQUEST);
        }
    } catch (Exception e) {
        if (e instanceof BusinessException) throw e;

        // Redis 장애 — 엔드포인트가 선언한 정책에 따라 분기
        if (strategy == LockStrategy.FAIL_OPEN) {
            log.error("Redis 연결 실패 - Fail Open 정책에 의해 로직 실행 허용");
        } else {
            throw new BusinessException(GlobalErrorCode.REDIS_CONNECTION_ERROR);
        }
    }
    return joinPoint.proceed();
}

② 장애 정책을 엔드포인트가 선언

// 메일 인증 발송 — Redis가 죽어도 가입은 계속되어야 하므로 FAIL_OPEN
@PreventDuplicateRequest(key = "#request.email", strategy = LockStrategy.FAIL_OPEN)
@PostMapping("/mail/send")
public ApiResponse<Void> sendAuthMail(@RequestBody EmailAuthRequest request) { ... }
의사결정 근거 — 왜 정책을 선택지로 만들었는가
메일 인증이 Redis 장애 때문에 막히면 회원가입 자체가 불가능해집니다. 중복 메일 두 통은 불편이지만 가입 불가는 장애입니다 → FAIL_OPEN. 반대로 결제처럼 중복 실행의 피해가 차단의 피해보다 큰 기능은 FAIL_CLOSE가 맞습니다. 즉 "장애 시 무엇을 포기할 것인가"는 기능마다 답이 다르고, 그 판단을 인프라 코드가 아니라 각 엔드포인트가 어노테이션으로 선언하게 했습니다.
결과
  • "따닥" 중복 요청이 비즈니스 로직 진입 전에 차단됩니다
  • Redis 장애 시의 동작이 엔드포인트별 선언으로 명시되어, 장애 상황의 동작을 코드만 보고 알 수 있습니다
  • 차단 로직이 AOP로 분리되어 비즈니스 코드에 중복 차단 코드가 섞이지 않습니다
03
Batch · Transaction

회원 탈퇴 — 유예 기간과 배치 삭제의 트랜잭션 설계

"한 명의 실패가 전체 배치를 멈추면 안 된다"
문제 원인

회원 탈퇴는 "DELETE 한 줄"이 아닙니다. 실수로 탈퇴한 사용자의 복구 요청은 실제로 존재하고, 사용자의 미디어 파일·프레임 데이터처럼 여러 도메인에 흩어진 데이터를 함께 정리해야 합니다. 그리고 이걸 배치로 처리할 때 가장 위험한 설계는 전체를 하나의 트랜잭션으로 묶는 것입니다 — 100명 중 1명의 삭제가 실패하면 99명의 삭제까지 롤백됩니다.

해결 과정

① 즉시 삭제 대신 7일 유예 — 상태 전환

// 탈퇴 요청 시점: 실제 삭제 없이 상태만 전환
user.updateStatus(UserStatus.DELETED_REQUESTED);

// 7일 안에 다시 로그인하면 복구 가능

② 자정 배치 — 유저 단위 트랜잭션 격리

// UserDeletionScheduler
@Scheduled(cron = "0 0 0 * * *")
public void run() {
    LocalDateTime threshold = LocalDateTime.now(clock).minusDays(7);

    List<Long> userIds = userRepository.findExpiredDeleteRequestedUserIds(
        UserStatus.DELETED_REQUESTED, threshold);

    for (Long userId : userIds) {
        try {
            // 유저마다 독립된 새 트랜잭션(REQUIRES_NEW)으로 처리
            userExitBatchService.exitInNewTransaction(userId);
        } catch (Exception e) {
            // 한 명의 실패는 기록만 하고 다음 유저로 — 전체 배치는 계속
            log.warn("[탈퇴 일괄처리 예외] 발생 유저 Id {}", userId, e);
        }
    }
}

③ 도메인별 정리는 DeletionHandler로 분리

// 유저 삭제 시 함께 정리할 것들을 도메인별 핸들러로 분리
// UserMediaDeletionHandler  — 사용자의 미디어 · S3 파일 정리
// FrameUserDeletionHandler  — 사용자의 프레임 데이터 정리
// 새 도메인이 생기면 핸들러 하나를 추가 — 탈퇴 로직 본체는 불변
의사결정 근거 — 트랜잭션 경계를 어디에 긋는가
"탈퇴 배치 전체가 원자적이어야 하는가?"를 먼저 물었습니다. 답은 아니오였습니다 — 유저 A의 삭제와 유저 B의 삭제는 서로 무관하므로, 원자성이 필요한 단위는 '유저 한 명'입니다. 그래서 유저별로 REQUIRES_NEW 트랜잭션을 열고, 실패는 로그로 격리했습니다. 실패한 유저는 상태가 그대로 남아 다음 날 배치가 자연스럽게 재시도합니다. 별도 재시도 큐 없이도 상태 기반 조회가 재시도를 겸하는 구조입니다.
결과
  • 탈퇴 후 7일 안에는 복구할 수 있어 실수 탈퇴 문의에 대응할 수 있습니다
  • 배치에서 한 명의 실패가 다른 유저의 삭제에 영향을 주지 않습니다
  • 실패 건은 상태가 유지되어 다음 배치에서 자동 재시도됩니다
Key Takeaways
01
파일은 서버의 일이 아닐 수 있습니다 — Presigned URL은 "업로드를 대신 해주는 것"이 아니라 "권한을 시간 제한으로 위임하는 것"이었습니다. 보안과 성능이 상충하지 않는 설계가 가능했습니다.
02
장애 시의 동작도 요구사항입니다 — FAIL_OPEN/FAIL_CLOSE는 "인프라가 죽었을 때 무엇을 포기할 것인가"라는 질문에 기능별로 답한 결과입니다. 이 판단은 인프라 코드가 아니라 기능이 선언해야 한다고 생각합니다.
03
트랜잭션 경계는 "무엇이 함께 실패해야 하는가"로 정합니다 — 배치 전체가 아니라 유저 한 명이 원자성의 단위였습니다. 경계를 잘못 그으면 격리가 아니라 연쇄 실패가 됩니다.
