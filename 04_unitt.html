01
Architecture · Spring Modulith

모놀리식으로 시작하되, 경계는 코드로 강제한다

"MSA를 겪어봤기 때문에 고를 수 있었던 선택"
문제 원인

코매칭 v5에서 MSA의 비용을 정면으로 치렀습니다. 서비스 간 호출, 데이터 정합성, 배포와 운영의 복잡도 — 트래픽 규모를 생각하면 명백한 오버엔지니어링이었습니다. 그렇다고 경계 없는 모놀리스로 돌아가면, 도메인들이 서로를 직접 참조하다가 나중에 분리하고 싶어도 분리할 수 없는 코드가 됩니다. "지금은 하나로, 그러나 언젠가 나눌 수 있게"가 요구사항이었습니다.

해결 과정

① Spring Modulith — 모듈 경계를 아키텍처 테스트로 검증

// ModularityTests.kt — 모듈 간 의존성 규칙을 어기면 테스트가 실패한다
@Test
fun verifiesModularStructure() {
    val modules = ApplicationModules.of(UnitBackendApplication::class.java)

    modules.verify()   // 허용되지 않은 모듈 간 참조 → 빌드 실패
}

② 모듈 간 참조는 객체가 아니라 ID로

// 다른 모듈의 엔티티를 직접 참조하지 않는다
// ❌ val member: Member          — 모듈 간 강결합, 분리 불가능
// ⭕ val memberId: Long          — 경계 밖은 식별자로만 참조

// 나중에 모듈이 별도 서비스로 분리되어도
// "ID로 조회하는 내부 API"로 바뀔 뿐, 도메인 코드는 그대로다
의사결정 근거
이 선택의 근거는 이론이 아니라 경험입니다. v5에서 "분산의 비용은 확실한데 이득은 우리 규모에서 없다"는 걸 확인했고, 동시에 "경계가 없으면 코드가 어떻게 엉키는지"도 v3에서 봤습니다. Spring Modulith는 그 중간을 줍니다 — 배포·트랜잭션·운영은 모놀리스의 단순함을 유지하면서, 모듈 경계는 컴파일·테스트 레벨에서 강제됩니다. 문서로만 존재하는 아키텍처는 반드시 무너진다는 걸 알기에, 경계 규칙을 CI에서 실패하는 테스트로 만들었습니다.
결과
  • 모듈 경계 위반이 테스트 실패로 즉시 드러나는 구조를 만들었습니다
  • 모듈 간 ID 참조 원칙으로 향후 서비스 분리 가능성을 열어뒀습니다
  • 주요 아키텍처 결정을 문서(ADR)로 기록해 "왜 이렇게 했는가"를 코드와 함께 남기고 있습니다
02
Auth · Design Decision

로그인을 시큐리티 필터가 아닌 서비스 API로

"코매칭에서 필터로 만들어봤기 때문에 내린 결정"
문제 원인

코매칭 v3에서는 로그인을 Spring Security의 커스텀 인증 필터로 구현했습니다. 동작은 했지만 불편함이 남았습니다 — 필터는 컨트롤러 어드바이스 바깥에서 동작하므로 공통 응답 포맷과 에러 코드를 맞추기 어렵고, 리프레시 토큰 저장·회원 상태별 분기 같은 도메인 로직이 시큐리티 설정 안에 숨어버립니다. 유니트에는 자체 로그인, 소셜 로그인, 학교 인증, 회원 상태 검증이 모두 필요했고, 이걸 필터 체인 안에서 관리하는 건 v3에서 겪은 불편을 반복하는 일이었습니다.

해결 과정

로그인은 명시적인 API로, 시큐리티는 토큰 검증에만

// 로그인은 평범한 서비스 API — POST /api/v1/auth/login
// 컨트롤러가 DTO를 검증하고, AuthLoginService가
// 이메일 해시 조회 → 비밀번호 검증 → 회원 상태 확인 → 토큰 발급을 수행

// Spring Security의 역할은 축소:
// 로그인 처리 X → JWT Resource Server로서 보호된 API의 토큰 검증·인가에 집중
의사결정 근거
로그인의 성공·실패는 프론트 인터셉터가 소비하는 API 계약입니다. 서비스 API로 만들면 공통 응답 구조와 회원 상태별 에러 코드를 다른 API와 동일하게 관리할 수 있고, 리프레시 토큰 저장·로테이션 정책이 로그인 흐름에 명시적으로 드러나며, 자체 로그인과 소셜 로그인이 같은 토큰 발급 정책으로 수렴합니다. 덤으로 REST Docs 테스트 대상이 되므로 로그인 계약도 테스트 기반으로 문서화됩니다. 필터로 만들어본 경험이 없었다면 이 트레이드오프를 판단하지 못했을 것입니다.
함께 설계한 것 — 리프레시 토큰의 동시성
리프레시 토큰은 해시로 저장하고 재발급 시 로테이션합니다. 여기에 한 가지 더 — 같은 토큰으로 동시에 재발급 요청이 들어오는 경합이 있습니다. 토큰 조회에 비관적 락(PESSIMISTIC_WRITE)을 걸어 로테이션 경로를 직렬화했습니다. 코매칭 v5의 RTR을 운영하며 생각했던 엣지 케이스를 이번 설계에 반영한 것입니다.
결과
  • 로그인 실패 응답이 다른 API와 동일한 공통 포맷으로 내려갑니다
  • 자체·소셜 로그인이 하나의 토큰 발급 정책을 공유합니다
  • 로그인 API 계약이 REST Docs로 테스트 기반 문서화됩니다
03
Test · Documentation

테스트가 통과해야 문서가 생성되는 구조

"배포 불안의 원인은 코드가 아니라 확신의 부재였다"
문제 원인

이전 프로젝트들에서 배포 전날의 불안을 반복해서 겪었습니다. 원인을 따져보면 코드가 나빠서가 아니라 "이 변경이 무엇을 깨뜨렸는지 확인할 방법이 없어서"였습니다. 테스트가 빈약하면 수동 확인에 의존하게 되고, 수동 확인은 회귀를 놓칩니다. API 문서도 마찬가지였습니다 — 손으로 쓰는 문서는 코드와 어긋나는 순간부터 거짓말이 됩니다.

해결 과정

Spring REST Docs — 문서를 테스트의 부산물로

// 테스트가 실제 요청/응답을 검증하고, 그 결과로 문서 조각이 생성된다
mockMvc.perform(post("/api/v1/auth/login")
        .contentType(MediaType.APPLICATION_JSON)
        .content(request))
    .andExpect(status().isOk)
    .andDo(document("auth-login",
        requestFields(
            fieldWithPath("email").description("로그인 이메일"),
            fieldWithPath("password").description("비밀번호")
        ),
        responseFields(...)
    ))

// 응답 필드가 바뀌었는데 문서를 안 고치면? → 테스트가 실패한다
// 즉, "문서가 코드와 다른 상태"가 빌드 단계에서 불가능해진다
의사결정 근거 — 왜 Swagger가 아니라 REST Docs인가
Swagger(springdoc)는 어노테이션만 붙이면 문서가 나오지만, 문서의 정확성을 아무도 검증하지 않습니다. REST Docs는 반대로 테스트를 통과한 요청/응답만 문서가 됩니다. 문서화 비용이 테스트 작성 비용에 흡수되는 대신, "문서에 있는 것은 실제로 동작한다"는 보장을 얻습니다. 테스트를 우선순위에 둔 프로젝트라서 고를 수 있는 선택지였습니다.
테스트의 범위 — 아키텍처까지
유닛·통합 테스트에 더해, 모듈 경계 규칙(ModularityTests)과 스키마 이력(Flyway)까지 "사람의 기억이 아니라 빌드가 검증하는 대상"으로 옮겼습니다. 배포 불안은 의지로 없어지지 않고, 검증을 자동화한 만큼만 줄어든다는 게 지금까지의 결론입니다.
결과
  • API 문서가 테스트를 통과한 요청/응답에서만 생성되어 문서와 코드의 불일치가 구조적으로 차단됩니다
  • 도메인 로직·API 계약·모듈 경계가 모두 테스트 대상입니다 (테스트 파일 60여 개, 개발 진행 중)
  • 변경 후 빌드 성공 = 회귀 없음에 가까워지도록 검증 범위를 계속 넓히고 있습니다
Key Takeaways
01
아키텍처는 경험의 함수입니다 — MSA를 겪지 않았다면 모듈러 모놀리스의 가치를 몰랐을 것입니다. "유행하는 것"이 아니라 "겪어본 문제를 해결하는 것"을 고르게 됐습니다.
02
규칙은 문서가 아니라 빌드로 지켜집니다 — 모듈 경계도, API 문서의 정확성도 사람의 주의력에 맡기면 반드시 무너집니다. 테스트로 강제할 수 있는 것은 전부 테스트로 옮기고 있습니다.
03
과거의 불편이 다음 설계의 근거가 됩니다 — 필터 로그인의 불편(v3), RTR의 엣지 케이스(v5), 배포 불안(전부). 유니트의 결정들은 대부분 이전 프로젝트에서 겪은 문제의 답입니다.
