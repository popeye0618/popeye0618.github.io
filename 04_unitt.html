01
Architecture · Modular Monolith

MSA 가 아니라 모듈러 모놀리스로 시작

"분리는 나중에, 경계는 지금"
문제 원인

기능 영역(사용자·학교 인증·판매글·거래·채팅·신고·관리자)은 명확히 나뉜다. 그렇다고 초기부터 MSA 로 가면 배포·분산 트랜잭션·운영 복잡도가 규모에 비해 과하다. 반대로 평범한 단일 모놀리스는 기능이 늘수록 패키지 의존성이 섞여 경계가 흐려진다. Comatching5 에서 MSA 를 해본 경험이 있었기에, 이번엔 "아직 MSA 가 필요한 단계가 아니다" 를 의식적으로 선택하되 경계만큼은 처음부터 강제하고 싶었다.

해결 과정

① Spring Modulith 로 모듈 경계를 코드로 검증

모듈을 platform / member / market / trade / ops 5개로 정의하고(ADR-0003), 모듈 간 의존성을 Spring Modulith 규칙으로 검증한다. 패키지 컨벤션이 아니라 테스트로 깨지는 경계다.

② 모듈 간에는 Entity 가 아니라 ID 로 참조

다른 모듈의 JPA Entity 를 직접 필드로 참조하면 내부 모델 변경이 그대로 전파된다. 그래서 외래키가 필요해도 코드에선 ID 값을 쓰고, 모듈 외부에 공개할 기능은 QueryService / CommandService 계약으로만 노출한다(ADR-0004).

③ 경계를 넘는 협력은 의존성 역전으로

// platform 모듈 — 인터페이스만 정의한다 (member 를 모름)
interface JwtAuthenticationValidator {
    fun isValid(jwt: Jwt): Boolean
}

// member 모듈 — 구현을 제공하고, platform 이 런타임에 주입받는다
@Component
@Transactional(readOnly = true)
class MemberStatusJwtAuthenticationValidator(
    private val memberRepository: MemberRepository,
) : JwtAuthenticationValidator {

    override fun isValid(jwt: Jwt): Boolean {
        val memberId = jwt.subject.toLongOrNull() ?: return false
        return memberRepository.existsByIdAndStatusInAndDeletedAtIsNull(
            id = memberId,
            statuses = listOf(MemberStatus.PENDING, MemberStatus.ACTIVE),
        )
    }
}
의사결정 근거
platform 은 인증이 끝난 뒤 "이 회원이 아직 유효한가" 를 묻고 싶지만, 회원 도메인을 알면 안 된다. 그래서 platform 이 인터페이스만 들고 있고 member 가 구현체를 제공한다. 덕분에 보안 필터는 member 모듈을 import 하지 않고도 회원 상태 검증을 호출할 수 있고, 나중에 member 를 별도 서비스로 떼어내도 이 계약은 그대로 남는다.
결과
  • 하나의 앱·하나의 포트로 운영 — 배포와 트랜잭션 관리가 단순
  • 모듈 의존성은 Modulith 테스트로 자동 검증 — 경계 위반이 빌드에서 드러남
  • ID 참조 + 공개 계약으로, 향후 특정 모듈만 서비스로 분리할 여지를 남김
02
Security · PII / Token

개인정보·토큰을 "털려도 덜 아프게"

"DB 가 유출돼도 피해 범위를 줄이려면"
문제 원인

이메일·전화번호·Refresh Token 은 로그인·중복확인·발송·세션 유지에 쓰이는 민감 정보다. 원문으로 저장하면 조회·발송은 쉽지만 DB 유출 시 그대로 노출되고, 단방향 해시만 저장하면 보안은 좋지만 메일 발송처럼 원문이 필요한 기능을 못 한다. 게다가 탈퇴를 soft delete 로 처리하다 보니, 단순 unique 제약은 탈퇴 회원 값 때문에 재사용을 막아버린다.

해결 과정

① 식별 정보를 해시 컬럼 / 암호화 컬럼으로 분리

@Entity
@Table(name = "users")
class Member(
    @Column(name = "email_hash", columnDefinition = "BINARY(32)")
    var emailHash: ByteArray? = null,        // SHA-256 — 로그인·중복확인 조회용

    @Column(name = "email_encrypted", columnDefinition = "VARBINARY(512)")
    var emailEncrypted: ByteArray? = null,   // AES-256-GCM — 발송이 필요할 때만 복호화

    @Column(name = "phone_hash", columnDefinition = "BINARY(32)")
    var phoneHash: ByteArray? = null,
    // ...
) {
    fun withdraw(now: LocalDateTime) {
        status = MemberStatus.DELETED
        deletedAt = now
        // 복호화 가능한 개인정보만 제거, 조회용 해시는 정책에 따라 보존
        emailEncrypted = null
        phoneHash = null
        passwordHash = null
    }
}

조회·중복확인은 정규화 후 SHA-256 해시로 비교하고, 발송처럼 원문이 필요한 경우에만 AES-256-GCM(랜덤 IV) 으로 암호화한 email_encrypted 를 복호화한다. Refresh Token·인증 코드는 원문 복원이 필요 없으므로 해시만 저장한다(ADR-0011).

② Refresh Token 은 해시로 저장하고 rotation

원문은 클라이언트에만 전달하고 서버에는 SHA-256 해시를 저장한다. 갱신 때마다 기존 토큰을 사용 처리하고 새 토큰을 발급하며, 상태를 ACTIVE → ROTATED → REVOKED / EXPIRED 로 추적한다(ADR-0007). 이미 사용된 토큰의 재사용을 막고, 로그아웃·탈퇴 시 서버에서 세션을 폐기할 수 있다.

③ 활성 회원 unique 제약은 generated column 으로

-- 탈퇴(soft delete) row 때문에 단순 unique 가 재사용을 막던 문제 해결
ALTER TABLE users
  ADD COLUMN active_email_hash BINARY(32)
    GENERATED ALWAYS AS (CASE WHEN deleted_at IS NULL THEN email_hash END) STORED,
  ADD UNIQUE KEY uk_users_active_email_hash (active_email_hash);
-- 활성 회원끼리만 unique. 탈퇴 회원은 값이 NULL 이라 제약에서 빠진다
의사결정 근거
목적을 컬럼 단위로 나눈 게 핵심이다. "조회·중복확인" 은 해시면 충분하고, "발송" 처럼 원문이 꼭 필요한 것만 양방향 암호화한다. 이렇게 분리해두면 탈퇴 시 복호화 가능한 정보만 지우고 운영에 필요한 해시는 남기는 정책이 깔끔해진다. MySQL 은 PostgreSQL 의 partial unique index 가 없어서, generated column + unique index 로 같은 효과를 냈다(ADR-0012).
결과
  • DB 가 유출돼도 이메일·전화번호 원문과 토큰 원문이 그대로 노출되지 않음
  • Refresh Token rotation 으로 재사용 차단 + 로그아웃·탈퇴 시 세션 폐기 가능
  • 탈퇴 회원을 보존하면서도 활성 회원 기준 unique 를 DB 레벨에서 보장
03
Transaction · Failure as State

실패도 남겨야 하는 도메인 상태다

"예외를 던지면서도 실패 기록은 남겨야 할 때"
문제 원인

학교 이메일 인증 코드가 틀리면 시도 횟수를 올려야 하고, 만료면 상태를 EXPIRED 로 남겨야 한다. 그런데 Spring 기본 트랜잭션은 RuntimeException 이 나면 전체를 롤백한다. BusinessException 을 던지기 전에 상태를 바꿔도 같은 트랜잭션이면 그 변경이 사라진다. 결과적으로 같은 코드가 계속 재처리되고, 시도 제한·보안 모니터링의 근거 데이터도 남지 않는다(ADR-0009).

해결 과정

① 실패 이력은 별도 트랜잭션(REQUIRES_NEW)으로 기록

@Component
class SchoolEmailVerificationFailureRecorder(
    private val repository: SchoolEmailVerificationCodeRepository,
) {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    fun recordMismatch(id: Long, maxAttemptCount: Int): Boolean {
        val code = repository.findById(id).orElseThrow()
        code.increaseAttempt()
        if (code.attemptCount >= maxAttemptCount) {
            code.expire()
            return true
        }
        return false
    }
}

본 트랜잭션이 실패 응답으로 롤백돼도, recorder 가 연 독립 트랜잭션에서 시도 횟수 증가·만료가 따로 커밋된다. 실패 상태 저장의 책임이 한 곳에 분명하게 모인다.

② 흐름이 단순한 곳은 noRollbackFor

@Transactional(noRollbackFor = [BusinessException::class])
override fun refresh(request: AuthTokenRefreshRequest): AuthTokenRefreshResponse {
    val currentToken = refreshTokenRepository.findByTokenHashAndStatus(tokenHash)
        ?: throw BusinessException(MemberErrorCode.INVALID_REFRESH_TOKEN)

    if (currentToken.expiresAt.isBefore(now)) {
        currentToken.expire(now)          // 이 상태 변경은 롤백되지 않는다
        throw BusinessException(MemberErrorCode.EXPIRED_REFRESH_TOKEN)
    }
    // ...정상 흐름: markUsed → rotate → 새 토큰 발급
}

③ 그리고 — JWT 인증 후 회원 상태 재검증

Access Token 은 stateless 라 탈퇴·정지 직후에도 만료 전까지 서명 검증을 통과한다. 그래서 인증이 끝난 뒤 인가 전에, ①에서 본 JwtAuthenticationValidator 로 현재 회원 상태(PENDING/ACTIVE, 미삭제)를 한 번 더 확인하고 아니면 401 을 돌려준다(ADR-0006). Redis blacklist 없이도 즉시 차단이 된다.

의사결정 근거
실패 횟수·만료는 버리는 값이 아니라 보안 모니터링과 운영 판단의 근거다. 응답은 실패로 주되 사실은 남겨야 한다. 그래서 성격에 따라 나눴다 — 반드시 이력을 남겨야 하는 곳은 REQUIRES_NEW recorder, 흐름이 단순한 만료 처리는 noRollbackFor. 둘 다 "예외를 던지면서도 상태는 보존" 이라는 같은 목표를 다른 비용으로 푼다.
결과
  • 실패 응답을 주면서도 시도 횟수·만료 상태가 롤백되지 않고 보존
  • 같은 코드가 반복 처리되는 문제 제거 — 시도 제한·감사 데이터 확보
  • stateless JWT 의 사각지대(탈퇴·정지 직후)를 상태 재검증 필터로 차단
Key Takeaways
01
경계는 도구가 아니라 규칙으로 강제한다 — Modulith + 모듈 간 ID 참조 + 의존성 역전. MSA 를 안 쓰기로 한 것도 설계 결정이고, 그 결정에 맞는 안전장치를 코드로 뒀다.
02
보안은 "털려도 덜 아프게" — 목적별로 해시/암호화 컬럼을 나누고, 토큰은 해시·rotation 으로 다룬다. 탈퇴 정책까지 컬럼 설계와 맞물려 움직인다.
03
실패는 기록해야 하는 도메인 상태 — 예외 롤백과 실패 저장을 분리하려고 REQUIRES_NEW 와 noRollbackFor 를 성격에 맞게 골라 썼다.
