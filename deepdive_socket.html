평소에 쓰던 HTTP 클라이언트와 WebSocket 라이브러리는 편리하지만, 그만큼 많은 것을 감추고 있습니다. 순수 Socket으로 HTTP 요청을 직접 조립하는 것에서 시작해, HttpClient → OkHttp → Retrofit → WebClient, 그리고 WebSocket → STOMP → SockJS → Netty → WebFlux까지 — 각 계층이 무엇을 대신해 주고 있었는지를 직접 구현하며 확인한 기록입니다.

Why This Deep Dive

시작은 단순한 질문이었습니다. "RestTemplate이나 WebClient를 호출하면, 그 아래에서는 실제로 무슨 일이 벌어지는가?" 답을 찾기 위해 업비트 OpenAPI라는 실제 대상을 두고, 가장 낮은 계층부터 같은 요청을 반복해서 구현했습니다. 소켓으로 HTTP 헤더를 문자열로 조립해 보면, 그 위의 모든 라이브러리가 "무엇을 자동화해 주는 도구"인지가 선명해집니다. 같은 방식으로 실시간 통신(WebSocket)과 서버 쪽 구현(Tomcat·Netty·WebFlux)까지 내려가 봤습니다.

Chapters
CHAPTER 01
HTTP 클라이언트 계층 — Socket부터 WebClient까지
SSLSocket으로 HTTP 요청을 직접 조립하는 것에서 시작해, HttpClient·OkHttp·Retrofit이 각각 무엇을 추상화하는지 확인합니다. 마지막으로 WebClient에서 블로킹과 논블로킹이 실제로 어떻게 다른지를 스레드 로그로 관찰합니다.
Raw Socket으로 HTTP 조립 native와 OS 커널 다이내믹 프록시 이벤트 루프 · epoll
CHAPTER 02
실시간 통신 — WebSocket, STOMP, SockJS
HTTP 연결을 업그레이드하는 핸드셰이크부터, STOMP 프레임을 NULL 문자까지 직접 조립해 보내는 실험, 그리고 방화벽에 막힌 WebSocket이 HTTP로 변장하는 SockJS 폴백까지. 업비트가 STOMP를 쓰지 않는 이유를 트레이드오프로 분석합니다.
Upgrade 핸드셰이크 STOMP 프레임 직접 조립 Backpressure — request(1) SockJS 폴백 실험
CHAPTER 03
서버의 관점 — Tomcat vs Netty vs WebFlux
연결 하나당 스레드 하나를 쓰는 톰캣, 이벤트 루프로 수만 연결을 감당하는 Netty, 그리고 스트림 파이프라인으로 추상화한 WebFlux까지 — 같은 웹소켓 서버를 세 방식으로 만들어 비교합니다. MVC와 WebFlux가 공존하기 어려운 이유도 여기서 확인했습니다.
Thread-per-Connection의 한계 EventLoopGroup · ChannelPipeline Flux 스트림 푸시 MVC vs WebFlux 공존 문제
