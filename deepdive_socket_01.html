Chapter 01

HTTP 클라이언트 계층
Socket부터 WebClient까지

같은 API(업비트 마켓 조회)를 다섯 가지 계층의 도구로 반복 구현했습니다. 가장 아래에서 문자열로 HTTP를 조립해 보면, 위 계층의 라이브러리들이 각각 무엇을 대신해 주는 도구인지가 선명해집니다.

SSLSocket HttpClient OkHttp Retrofit2 WebClient
01
Raw Socket

소켓으로 HTTP 요청을 직접 조립하기

"HTTP는 결국 규격에 맞춘 문자열이다"
소켓의 아래에서 벌어지는 일

자바에서 Socket으로 텍스트를 전송하면, 요청은 native 메서드를 통해 JVM으로 넘어갑니다. native란 자바에는 선언(껍데기)만 있고 실제 구현은 C 파일에 있는 메서드입니다 — OS 커널과 직접 대화할 수 있는 언어가 C이기 때문입니다. JVM이 C 함수를 실행하면 OS 커널의 TCP/IP 스택이 데이터 앞뒤에 TCP 헤더와 IP 헤더를 붙여 패킷을 만들고, 커널이 랜카드(NIC)를 통해 인터넷 망으로 내보냅니다. 우리가 쓰는 모든 HTTP 라이브러리는 이 경로 위의 포장지입니다.

직접 구현

요청은 문자열 조립, 응답은 빈 줄로 헤더/바디 분리

// HTTP 요청을 규격 그대로 문자열로 조립한다
String httpRequest =
        "GET /v1/market/all HTTP/1.1\r\n" +
        "Host: " + host + "\r\n" +
        "accept: application/json\r\n" +
        "Connection: close\r\n" +
        "\r\n";                              // 빈 줄 = 헤더의 끝

SSLSocketFactory factory = (SSLSocketFactory) SSLSocketFactory.getDefault();

try (SSLSocket socket = (SSLSocket) factory.createSocket(host, port);
     PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
     BufferedReader in = new BufferedReader(new InputStreamReader(socket.getInputStream()))) {

    out.print(httpRequest);
    out.flush();

    String line;
    boolean isBody = false;
    StringBuilder body = new StringBuilder();

    while ((line = in.readLine()) != null) {
        if (line.isEmpty()) { isBody = true; continue; }  // 빈 줄 이후가 바디
        if (isBody) body.append(line);
        else System.out.println("[Header] " + line);
    }
}
여기서 확인한 것
HTTP는 "빈 줄(\r\n)로 헤더와 바디를 구분하는 텍스트 규격"일 뿐입니다. 헤더 한 줄의 오타, 마지막 빈 줄 누락 — 어느 하나만 틀려도 서버는 응답하지 않습니다. 평소 라이브러리가 던져주던 "잘 파싱된 응답 객체"가, 사실은 이 원시 스트림을 누군가 대신 읽고 잘라준 결과라는 걸 처음으로 체감했습니다.
02
HttpClient · OkHttp · Retrofit

한 겹씩 올라가며 — 각 계층이 대신해 주는 것

"라이브러리 선택은 '무엇을 자동화받을 것인가'의 선택이다"
① HttpClient — 소켓을 감싼 표준 인터페이스 (Java 11+)
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.upbit.com/v1/market/all"))
        .header("accept", "application/json")
        .GET()
        .build();

HttpResponse<String> response = HttpClient.newHttpClient()
        .send(request, HttpResponse.BodyHandlers.ofString());

주소의 https://를 보고 보안 소켓(TLS) 처리를 자동으로 해주고, 소켓에서 직접 하던 헤더/바디 분리를 대신 해주며, 빌더 패턴으로 요청 조립의 실수를 막아줍니다. 제가 Story 01에서 손으로 했던 일들이 정확히 이 도구의 기능 목록입니다.

② OkHttp — 같은 역할, 더 정교한 운영 기능

OkHttp도 순수 소켓을 숨기고 헤더와 URL을 다루기 쉽게 만든 상위 레벨 클라이언트라는 점은 HttpClient와 같습니다. 차이는 연식과 완성도입니다 — HttpClient는 Java 11에서 나왔지만 OkHttp는 그전부터 발전해 왔고, 불안정한 네트워크에서의 자동 재시도, 캐싱, 그리고 연결을 끊지 않고 재사용하는 Connection Pool이 훨씬 정교하게 구현되어 있습니다. "표준이냐, 검증된 운영 기능이냐"가 선택 기준이 됩니다.

③ Retrofit2 — 보일러플레이트를 인터페이스 선언으로
// 요청 명세를 자바 인터페이스로 선언하면 끝
public interface UpbitApiService {
    @GET("/v1/market/all")
    Call<List<UpbitMarket>> getAllMarkets(@Header("accept") String accept);
}

Retrofit retrofit = new Retrofit.Builder()
        .baseUrl("https://" + host)
        .client(new OkHttpClient())
        .addConverterFactory(GsonConverterFactory.create())   // JSON → 자바 객체 자동 변환
        .build();

List<UpbitMarket> markets = retrofit.create(UpbitApiService.class)
        .getAllMarkets("application/json").execute().body();  // 이미 객체로 변환되어 도착
핵심 원리 — 다이내믹 프록시
인터페이스만 선언했는데 어떻게 동작할까요? Retrofit은 실행 시점에 임시 구현 클래스를 만들어 네트워크 코드를 채워 넣습니다(다이내믹 프록시). 즉 소켓 생성 → 헤더 문자열 조립 → 스트림 전송 → 응답 수신 → 헤더/바디 분리 → UTF-8 변환 → JSON 파싱이라는, 제가 아래 계층에서 직접 했던 전 과정을 어노테이션 몇 개로 자동화하는 것입니다. Spring Data JPA가 리포지토리 인터페이스로 하는 일과 같은 원리라는 점도 흥미로웠습니다.
03
WebClient · Non-Blocking

블로킹과 논블로킹 — 스레드 로그로 관찰하기

"요청을 던진 스레드와 응답을 받은 스레드가 다르다"
문제 의식

지금까지의 Socket, HttpClient, OkHttp, Retrofit은 모두 블로킹 방식입니다 — 요청을 보낸 스레드가 응답이 올 때까지 기다립니다. 사용자가 몰려 동시에 외부 API를 호출하면 서버의 스레드 전부가 "기다리는 일"에 묶여 메모리와 CPU를 낭비하고, 시스템이 불안정해집니다. 논블로킹은 요청을 던져놓고 스레드가 다른 일을 하러 가는 방식이라, 몇 개의 스레드로도 수만 건의 동시 요청을 처리할 수 있습니다.

직접 관찰

실행 순서가 1 → 2 → 3, 그리고 스레드가 바뀐다

System.out.println("[1] 요청을 조립하고 서버로 던집니다. (스레드: " + Thread.currentThread().getName() + ")");

Mono<List<UpbitMarket>> responseMono = webClient.get()
        .uri("/v1/market/all")
        .retrieve()
        .bodyToMono(new ParameterizedTypeReference<>() {});

responseMono.subscribe(markets -> {
    System.out.println("[3] 데이터 응답 완료! (스레드: " + Thread.currentThread().getName() + ")");
    latch.countDown();
});

System.out.println("[2] 기다리지 않고 바로 다음 줄로 내려왔습니다. (스레드: " + Thread.currentThread().getName() + ")");
latch.await();
// 실행 결과
[1] 요청을 조립하고 서버로 던집니다.        (스레드: Test worker)
[2] 기다리지 않고 바로 다음 줄로 내려왔습니다. (스레드: Test worker)
[3] 데이터 응답 완료!                      (스레드: reactor-http-nio-2)
직접 구현해보고 바로잡은 오해
처음에는 webClient.get()이 요청을 보내는 줄 알았습니다. 실제로는 get()~bodyToMono()는 설계도만 만들고, subscribe()가 호출되는 순간 실제 요청이 나갑니다. 이걸 알고 나니 구조가 보였습니다 — 원래 스레드(Test worker)는 위임만 하고 지나가고, 전혀 다른 스레드(reactor-http-nio)가 미래의 어느 시점에 응답을 받아 처리합니다. 또 하나 — Mono와 Flux의 구분 기준은 데이터 개수가 아니라 "받는 횟수"였습니다. 여러 건을 List로 한 번에 받으면 Mono입니다. 지속적으로 여러 번 받는 Flux는 WebSocket과 닮아 있었고, 이 관찰이 다음 챕터(실시간 통신)로 이어졌습니다.
응답은 어떻게 감지되는가 — 이벤트 루프와 epoll

로우레벨 소켓에서는 read()에서 스레드가 멈춰 응답을 기다렸습니다. 스레드가 멈추지 않는데 도착을 어떻게 알까요? WebClient 아래의 Netty 엔진은 자바 NIO를 사용해 OS 커널에 "데이터가 도착하면 이벤트를 달라"고 등록해 둡니다. 이 커널 기능이 리눅스의 epoll(macOS는 kqueue)입니다. 내부에는 이벤트 루프라는 전용 스레드 몇 개만 살아서 무한 루프를 돌며 대기하는데, 계속 일하는 게 아니라 OS가 신호를 줄 때만 일합니다. 서버가 보낸 패킷이 랜카드에 도착하면 커널이 소켓 버퍼를 채우고 이벤트 루프를 깨우고, 이벤트 루프가 버퍼에서 데이터를 꺼내 subscribe()에 등록된 가공 파이프라인으로 넘깁니다.

Chapter Takeaways
01
모든 HTTP 라이브러리는 같은 원시 경로 위의 포장지입니다 — 소켓으로 한 번 조립해 보니, 계층별 도구의 기능 목록이 "내가 손으로 했던 일들"과 정확히 일치했습니다.
02
논블로킹의 실체는 "OS에 등록하고 신호를 기다리는 것"입니다 — 마법이 아니라 epoll과 이벤트 루프라는 구체적인 메커니즘이었고, 스레드 로그로 직접 확인했습니다.
03
선언과 실행의 분리를 이해하면 리액티브가 읽힙니다 — "설계도 작성(Mono 조립)"과 "실행(subscribe)"이 분리되어 있다는 것을 모르면 리액티브 코드는 계속 마법처럼 보입니다.
