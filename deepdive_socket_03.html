Chapter 03

서버의 관점
Tomcat vs Netty vs WebFlux

클라이언트를 계층별로 구현했으니, 이번엔 반대편입니다. 같은 웹소켓 서버를 세 가지 방식으로 구현하며 — 연결마다 스레드를 쓰는 톰캣, 이벤트 루프로 감당하는 Netty, 스트림으로 추상화한 WebFlux — 각 모델이 무엇을 감당할 수 있고 무엇을 포기하는지 확인했습니다.

Spring WebSocket (Tomcat) Netty Spring WebFlux Reactor
01
Spring WebSocket · Tomcat

익숙한 방식 — 연결 하나에 스레드 하나

"연결이 유지되는 통신에서 이 모델의 비용은 다르게 계산된다"
구현
// 서버 — TextWebSocketHandler를 상속해 이벤트별 동작 정의
public class SpringWebSocketHandler extends TextWebSocketHandler {

    @Override
    public void afterConnectionEstablished(WebSocketSession session) throws Exception {
        session.sendMessage(new TextMessage("연결 완료"));
    }

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws Exception {
        session.sendMessage(new TextMessage("서버의 메아리: " + message.getPayload()));
    }
}

// 설정 — registry에 핸들러와 경로 등록
@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new SpringWebSocketHandler(), "/pure-ws")
                .setAllowedOrigins("*");
    }
}
이 모델의 한계
스프링 MVC 방식의 웹소켓은 톰캣 위에서 돌고, 톰캣은 기본적으로 연결 하나당 스레드 하나를 씁니다. HTTP처럼 금방 끝나는 요청이라면 스레드가 곧 반납되지만, 웹소켓은 연결을 계속 들고 있는 통신입니다. 사용자 수만 명이 소켓을 열어두면 스레드도 수만 개가 필요하고, 스레드마다 스택 메모리가 잡히므로 서버 메모리가 감당하지 못합니다. "요청-응답에는 합리적이던 모델이, 연결 유지형 통신에서는 병목이 된다" — 이 차이를 확인하려고 다음 두 구현을 만들었습니다.
02
Netty

Netty — 이벤트 루프로 수만 연결 감당하기

"스레드를 CPU 개수만큼만 띄우고 돌아가면서 처리한다"
구현
public class NettyWebSocketServer {
    public static void main(String[] args) throws Exception {
        EventLoopGroup bossGroup = new NioEventLoopGroup(1);  // 새 연결 접수 전담 (1개)
        EventLoopGroup workerGroup = new NioEventLoopGroup();  // 데이터 처리 일꾼 (기본 CPU 코어 × 2)

        ServerBootstrap b = new ServerBootstrap();
        b.group(bossGroup, workerGroup)
         .channel(NioServerSocketChannel.class)          // 논블로킹 서버 채널
         .childHandler(new ChannelInitializer<SocketChannel>() {
             @Override
             protected void initChannel(SocketChannel ch) {
                 ChannelPipeline pipeline = ch.pipeline();
                 pipeline.addLast(new HttpServerCodec());                       // HTTP 인코딩/디코딩
                 pipeline.addLast(new HttpObjectAggregator(65536));             // 조각난 메시지 합치기
                 pipeline.addLast(new WebSocketServerProtocolHandler("/netty-ws")); // 핸드셰이크·프레임 처리
                 pipeline.addLast(new NettyWebSocketServerHandler());           // 우리 비즈니스 로직
             }
         });

        ChannelFuture f = b.bind(8080).sync();   // bind도 비동기 — sync()로 완료를 기다린다
        f.channel().closeFuture().sync();
    }
}
구조 해부

ServerBootstrap은 스레드 그룹·소켓 종류·파이프라인을 한곳에 모아 조립하는 빌더입니다. NioServerSocketChannel은 서버에 딱 하나 열리는 "정문"으로, 새 연결 요청(accept)만 감지합니다. 핸드셰이크가 성공하면 클라이언트마다 전용 SocketChannel이 생기고 — 만 명이면 만 개 — 채널 하나하나에 독립된 파이프라인이 깔립니다. 그런데 스레드는? worker 몇 개가 전부입니다. Chapter 01에서 본 이벤트 루프가 서버 쪽에서도 같은 원리로 동작합니다 — 채널에 데이터가 도착하면 OS가 이벤트 루프를 깨우고, 깨어난 일꾼이 해당 채널의 파이프라인을 실행합니다.

놓치기 쉬운 포인트 — sync()의 의미
Netty의 모든 작업은 논블로킹이라 b.bind(8080)을 호출해도 포트가 열리기를 기다리지 않고 다음 줄로 넘어갑니다. 그래서 ChannelFuture에 .sync()를 붙여 완료를 기다립니다 — Chapter 02에서 쓴 CountDownLatch와 같은 역할을 Netty 방식으로 하는 것입니다. "비동기 프레임워크에서는 '완료를 기다리는 지점'을 명시적으로 골라야 한다"는 감각이 여기서 생겼습니다.
03
Spring WebFlux

WebFlux — 소켓 스트림을 Flux 파이프라인으로

"그리고 MVC와 WebFlux는 왜 같이 못 쓰는가"
구현
// 서버 — 1초마다 데이터를 무한히 푸시하는 Flux 파이프라인
@Component
public class ReactiveWebSocketHandler implements WebSocketHandler {

    @Override
    public Mono<Void> handle(WebSocketSession session) {
        Flux<String> sourceFlux = Flux.interval(Duration.ofSeconds(1))
                .map(seq -> "실시간 서버 푸시 데이터 [No." + seq + "]");

        return session.send(sourceFlux.map(session::textMessage));
    }
}

// 클라이언트 — 스트림에서 5개만 받고 안전하게 종료
client.execute(url, session ->
        session.receive()
               .map(WebSocketMessage::getPayloadAsText)
               .doOnNext(text -> System.out.println("[실시간 수신] " + text))
               .take(5)      // 5개 수신 후 스트림 종료 — 파이프라인이 정리를 책임진다
               .then())
      .subscribe();

Netty에서는 데이터가 올 때마다 핸들러 메서드가 깨어나고, 복잡한 처리는 그 안에 코드를 쌓아야 했습니다. WebFlux는 같은 Netty 엔진 위에서 들어오는 소켓 데이터를 하나의 Flux 스트림으로 포장해 주므로, 수신 → 변환 → 부수효과 → 종료 조건까지가 선언형 파이프라인 한 줄로 표현됩니다.

부딪힌 문제 — MVC와 WebFlux의 공존

모든 코드를 한 프로젝트에서 돌리고 싶었지만, 마지막 Reactive 구현만은 실행할 수 없었습니다. "MVC와 WebFlux는 같이 못 쓴다"는 말을 어렴풋이 알고 있었는데, 이참에 이유를 파봤습니다.

왜 충돌하는가
두 의존성이 함께 있으면 스프링부트 자동 설정은 톰캣을 선택합니다. 문제는 철학입니다 — MVC의 DispatcherServlet은 기본적으로 동기 구조라, 컨트롤러가 Mono/Flux를 반환해도 결국 응답을 기다리는 쪽으로 수렴합니다. 반면 WebFlux는 "스레드는 절대 차단되지 않는다"는 가정 아래 스레드를 CPU 코어 수만큼만 만듭니다. 몇 개 없는 스레드가 차단되기 시작하면 스레드 고갈이나 데드락으로 이어집니다.
그런데 WebClient는 왜 MVC에서 써도 되는가
WebClient는 서버가 아니라 외부로 요청을 보내는 클라이언트이기 때문입니다. MVC 환경에서 호출하면, 톰캣 스레드가 결과를 기다리는 동안 WebClient 내부의 리액티브 스레드가 응답을 받아 전달해 줍니다. 즉 WebClient만 리액티브하게 일하고 결과는 톰캣 모델에 맞춰주는 것은 가능합니다 — "서버 전체의 실행 모델"과 "클라이언트 도구의 내부 구현"은 별개라는 걸 확인했습니다.
Chapter Takeaways
01
스레드 모델은 통신 패턴에 따라 비용이 달라집니다 — 요청-응답에서 합리적인 thread-per-connection이, 연결 유지형 통신에서는 메모리 병목이 됩니다. 같은 모델도 문맥이 바뀌면 평가가 바뀝니다.
02
Netty를 알면 그 위의 추상화가 읽힙니다 — boss/worker 이벤트 루프와 채널 파이프라인을 직접 조립해 보니, WebFlux가 "무엇을 Flux로 포장해 주는지"가 명확해졌습니다.
03
프레임워크의 제약에는 실행 모델의 이유가 있습니다 — MVC와 WebFlux의 충돌은 금지 규칙이 아니라 "차단 가정이 다른 두 모델은 섞이면 고갈된다"는 구조적 귀결이었습니다.
